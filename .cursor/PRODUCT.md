# Скрипка — продукт

Скрипка — контроль строительства. Сопоставляет **план** (график объекта → `ExpectedState`) с **фактом** (наблюдение / CV → `ActualState`) и даёт инспектору объяснимый сигнал. Решение принимает человек.

Цепочка ценности:

```text
что должно быть → что наблюдается → что изменилось → в чём отклонение
→ насколько требует внимания → на каких кадрах → что проверить человеку
```

Язык сигналов: «наблюдаемый факт», «признак исполнения», «возможное отклонение», «требуется проверка». Система не подтверждает окончательное положение без решения инспектора. Запрещены формулировки вроде «строительство остановлено», «подрядчик нарушил», «не соответствует проекту».

## Сущности (контур)

```text
CURRENT: площадка → объект → источники → график
         → observation → ActualState → plan/fact deviation → Alert → решение инспектора

TARGET:  + вид строительства → справочник работ;
         + признак исполнения пункта плана (не вердикт) в workspace объекта
```

| Сущность | Смысл |
|----------|--------|
| Площадка (project) | Контейнер объектов и рабочего контекста |
| Объект | Backend: `Zone`. UI: «объект» |
| Описание объекта | Идентичность и реквизиты объекта |
| Вид строительства | **TARGET.** Определяет, какие работы вообще возможны |
| Источники | Камеры, видео, фото; материалы инспектора — целевой контур |
| График объекта | Конкретные работы, сроки и последовательность на объекте → `ExpectedState` |
| Observation / ActualState | Наблюдаемый факт по кадру/видео/CV |
| Plan/fact deviation | **CURRENT.** Сравнение Expected vs Actual → сигнал |
| Исполнение пункта плана | **TARGET.** Признаки по пункту графика (не юридический вердикт); отдельной сущности в runtime нет |
| Решение инспектора | `confirmed` / `rejected` / `needs_more_data` + причина |

**Ожидаемое состояние** — производная **графика конкретного объекта**, не справочника работ.

**xlsx ≠ КСГ.** Файл `ТЗ /Датасет /7.ДГП_датасеты/Сводный перечень строительных работ_ЛТЦ.xlsx` — справочник видов/наименований строительных работ по виду строительства. Это не календарный график, не содержит фактические сроки объекта и сам по себе не становится `ExpectedState`. Если у объекта нет отдельного графика — сроки не выдумывать.

Три каталога не смешивать:

1. `config/equipment_rules.yaml` — каталог этапов MVP → `GET /api/catalog/stages`
2. Пользовательский import КСГ (csv/xlsx/json через `parse_ksg`) — график конкретного объекта
3. DGP xlsx — справочник работ по виду строительства (`sitewatch/catalog/construction.py` → `GET /api/catalog/construction-types` и `.../{id}/works`). Строки графика из справочника создаются только с датами.

`housing_16` / `catalog.json` — отдельный experimental slice, не справочник DGP.

## Текущая реализация / Current implementation

### MVP-сценарии demo (`site_001`)

1. **Техника (котлован)**  
   `zone_a` NORMAL (excavator + 3 dump_truck).  
   `zone_b` `missing_equipment` (dump_truck=0 при min=2).

2. **Динамика корпуса**  
   `building_01`, камера `cam_building`, даты 01 / 08 / 15 / 22.09.  
   Факт: 4 перекрытия → 4 этажа. КСГ: 4 → 4 → 5 → 6 этажей.  
   Сигнал: `no_dynamics` + при необходимости `schedule_delay` / `missing_element`.  
   Формулировка: «Выявлены признаки отсутствия строительной динамики. Требуется проверка.»

3. **Контур инспектора**  
   Открытые сигналы на `/signals`, brief «что проверить», решение `confirmed` / `rejected` / `needs_more_data` с причиной из `config/inspector.yaml`. Fingerprint не плодит дубликаты при повторном evaluate.  
   UI: `POST /api/alerts/{id}/decision`. `/api/queue` — legacy alias бэкенда на open alerts (не главный экран).

### Plan / Fact (как работает сейчас)

- **Plan:** график объекта (`ScheduleStage`) → `build_expected_state()` в evaluate → `ExpectedState` / `ExpectedStateRecord`. Нет КСГ на дату → evaluate `ValueError`; observe всё равно пишется.
- **Fact:** фото / камера / видео / CV → observation → `ActualState` / `ActualStateRecord`.
- Цепочка: source → observation → CV evidence → `ActualState` → сравнение с `ExpectedState` → signal → inspector review.
- CV не пишет юридический или управленческий вердикт.
- Отдельной сущности «исполнение пункта плана» / execution tracker **нет**. Есть plan/fact, deviation и этапы из `equipment_rules.yaml`.

### Источники (как есть в runtime)

Камеры: `uri`, `enabled` (default true), `interval_minutes` (5–1440, default 30), `last_captured_at`, `last_error`.  
Пустой `uri` → захват `skipped`, «Снять сейчас» disabled. Отключённая камера не участвует в захвате. Удаление камеры с наблюдениями → HTTP 409 («disable the source instead») — отключать, не удалять.  
Загрузка кадров/видео — через observe / capture. Полноценных отдельных сущностей «загруженное видео / фотоархив / материалы инспектора» как first-class типов пока нет.

### Каталог этапов MVP

`GET /api/catalog/stages` → `catalog.py` → `equipment_rules.yaml` (`stages.{code}.label`, required/unexpected equipment).  
KsgEditor: dropdown этапов + CRUD графика; import `.csv/.xlsx/.xls/.json` через `parse_ksg` → `ScheduleStage` в SQLite. Любой xlsx-import графика ≠ чтение файла ДГП.

### Классы CV (видимые)

`foundation`, `column`, `wall`, `slab`, `roof`, `window`, `facade` + техника.  
`floors` — производная величина, не bbox-класс.  
Рабочий demo-детектор — `annotation` (sidecar). YOLO-адаптер есть, production-весов construction-модели в репо нет. Синтетическое demo media не выдавать в UI как production ML.

### Стек MVP

Python, PyTorch/Ultralytics (опционально), OpenCV, FastAPI, React (Vite), SQLite.  
SAM 2 / DINOv2 / PaddleOCR — слоты. ByteTrack — video path.

### Приоритет

frontend/UX → ingest реальных фото/видео → реальный CV → реальная КСГ.

### Не продукт (anti-goals)

BIM parser, 4D BIM, digital twin, RT-DETR, SAM 3, собственная VLM-вердикт, модель «остановка стройки», полный 3D/COLMAP, автоопределение всех видов работ, микросервисы, Kubernetes, PostgreSQL «на будущее», новый CV framework.

## Целевое состояние / Target product state

### Вид строительства и график

Вид строительства определяет набор возможных работ.  
График объекта задаёт, какие работы, когда и в какой последовательности идут на **этом** объекте.  
Поля объекта и список работ в будущем приходят из API по виду строительства — этого API ещё нет. Сроки — только из графика объекта.

### Создание объекта (доменный сценарий)

Кнопка «Объект» запускает создание:

1. описание объекта  
2. выбор вида строительства  
3. поля, зависящие от вида строительства  
4. подключение источников видео  
5. загрузить существующий график **или** создать график на основании вида строительства  
6. открытие рабочего пространства объекта  

Конкретный wizard/компоненты и URL не фиксируются. `/setup` — текущий админ-контур площадки, не целевой сценарий создания.

### Источники (целевая модель)

Камеры, загруженные видео, фотографии, инспекторские материалы.  
Заметки и отметки исполнения по кадрам — продуктовые сущности целевого контура.

### Исполнение пункта плана

Видеоаналитика может создавать **признаки**: наблюдается / вероятно началась / вероятно выполнена / не наблюдается / возможное отклонение / требуется проверка.  
Окончательный вердикт — только инспектор.  
**Ещё не реализовано** как отдельный tracker в runtime.

### Workspace объекта

Единое рабочее окно: график, источники, загруженные фото, наблюдения, заметки, история, evidence, состояние исполнения пунктов плана.  
Маршруты целевых экранов не выдумывать — описывать сценарием.

### Ответственность

Автоматика ведёт до сигнала (наблюдение → ActualState → сравнение → alert).  
Решение о подтверждении положения — отдельно, человеком (`confirmed` / `rejected` / `needs_more_data`).
