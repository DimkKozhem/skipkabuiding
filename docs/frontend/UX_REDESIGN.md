# Скрипка — спецификация интерфейса

Статус: целевой UX следующей версии. Не патч текущих файлов.  
Источник: живой SPA `http://127.0.0.1:8000` (2026-09-20), React `frontend/src/`, API `/api/*`, demo `site_001`.  
Не опираться на README.

Параллельный frontend-агент реализует UI по этому документу. Backend-контракты не ломать. Где данных не хватает — таблица §14.

---

## 0. Как читать документ

Каждый экран отвечает на один вопрос инспектора. Если блок не помогает ответить — его нет в главном UI.

Правильная семантика продукта (не менять):

```text
обнаружены признаки
возможное отклонение
нет наблюдаемой динамики
требуется проверка
```

Запрещено в UI: «стройка остановлена», «нарушение доказано», «система подтвердила».

Demo-объект: **ЖК Северный**. Три зоны наблюдения:

| code | Имя в UI | Сюжет |
|------|----------|--------|
| `zone_a` | Котлован А | норма: экскаватор 1, самосвал 3 |
| `zone_b` | Котлован Б | `missing_equipment`: самосвал 0 при ≥2 |
| `building_01` | Корпус 1 | план этажей 4→5→6, факт 4→4→4; `no_dynamics` + `schedule_delay` |

`code` и `site_001` не являются заголовками. Это технические идентификаторы.

## 1. Executive summary

Человек впервые открывает Скрипка. За 30 секунд он должен увидеть:

1. На площадке **5 ситуаций, которые система просит проверить** (не «5 алертов в БД»).
2. Самое важное — **Корпус 1: план 6 этажей, наблюдается 4**. Рядом кадр.
3. **Котлован Б: ждали ≥2 самосвала, видно 0**.
4. **Котлован А в порядке** — проверять не нужно, это тоже информация.

Главный визуальный язык продукта:

```text
Ожидалось          Наблюдается
≥ 2 самосвала      0
6 этажей           4 этажа
+2 этажа / 21 день 0 изменений
```

Это не KPI-wall и не JSON-консоль. Это рабочее место инспектора: сигнал → сравнение плана и факта → кадры → что проверить на площадке → решение человека.

Текущий frontend — прототип пайплайна: шесть пунктов меню, сырой JSON, UUID наблюдений, английские rationale, дубли «Очередь» / «Alerts», таблица «4 / 12 / 4 / да». Домен уже умеет почти всё, что нужно для сильного UI. Сначала собрать смысл из существующих DTO, не придумывать новый продукт.

## 2. Current UX problems

Зафиксировано проходом как новый пользователь (стартовая страница `/` = «Инспекция», затем Dashboard, Очередь, Объект, Timeline, Alerts).

### Что понятно сразу

- Название и слоган: факт фиксирует CV, решение принимает инспектор.
- Есть фото и overlay.
- У Котлована А зелёный текст «отклонений не обнаружено».
- У Котлована Б в колонке DEVIATIONS уже есть человеческий абзац «Самосвал — минимум 2 / 0».
- Очередь инспектора — единственный экран, где есть смысл работы: чеклист «что проверить» и форма решения.

### Что непонятно за 30 секунд

- Зачем старт с «Инспекция: Plan ↔ Fact» и цепочки `КСГ → Expected → Observation → …`. Это карта бэкенда, не задача пользователя.
- Три пункта меню про одно и то же: Инспекция, Очередь, Alerts.
- Dashboard — 8 плиток (`3 / 5 / 2 / 2 / 0 / 0 / 0 / 1`) и три JSON-дампа. Неясно, что делать первым.
- Корпус 1 выглядит как «4 открытых сигнала», без картинки «план 6 / факт 4».
- Timeline вешает «Нет динамики» на **01.09**, хотя в этот день план = факт = 4. Пользователь думает, что система ошибается.

### Куда хочется нажать

- На фото.
- На текст отклонения.
- На карточку зоны.

Сейчас кликабельны в основном пункты сайдбара, `<select>` demo-сценариев и «Открыть объект» под JSON.

### Где нет визуального приоритета

- На Инспекции три равные колонки: детекции / JSON / отклонения. Отклонение должно быть первым.
- На Dashboard все зоны одинакового веса. Корпус 1 с 4 сигналами визуально равен спокойному Котловану А.
- 22 строки `column 0.84` в таблице детекций кричат громче, чем этажность.

### Где приходится угадывать смысл

- `DEMO 1 — NORMAL · zone_a` — внутренний ярлык сценария, не имя объекта.
- `Этап: excavation` на Dashboard, хотя в API уже есть `stage_label: «Разработка котлована»`.
- `schedule_progress=4.0` в тексте `no_dynamics`. Это сумма дельт `floors+slabs+columns+walls` (2+2+0+0), **не** «4 этажа прогресса». Показывать сырым числом нельзя.
- `Observation #23eb7200`, `source=annotation`, `model=0.8414 · evidence=0.75 · rule=0.6`.
- Статус объекта `ok | deviation` vs статус сигнала `open`. На Объекте пишется `Нет динамики · open`.

### Какие страницы — developer UI

| Страница | Почему |
|----------|--------|
| Инспекция `/` | JSON Expected/Actual, UUID, таблица классов, pipeline в лиде |
| Dashboard `/dashboard` | KPI + `JsonBlock` |
| Объект `/object` | два JSON и простыня `message` |
| Timeline `/timeline` | склейка метрик `4 / 12 / 4 / да`, полный `message` на каждую дату |
| Alerts `/alerts` | дубль очереди, заголовок «Сигналы надзору» |
| Очередь `/queue` | правильная задача, но карточка = две строки, справа — сырой `message` + JSON expected/observed |

`JsonBlock` используется как основной виджет состояния. Это и есть прототип.

### Что спрятано слишком глубоко

- Смысл Корпуса 1 (4→5→6 vs 4→4→4) живёт в `PlanFactTable` **только** на Инспекции и только после выбора `building_01`, ниже fold.
- `GET /projects/:code/zones/:zone` уже отдаёт `ksg[]` (ряд плана) — UI игнорирует.
- Человеческие имена зон («Котлован А») есть в dashboard, в очереди показывается `building_01`.
- `deviation.title`, `expected`, `observed` есть в `GET /alerts/:id`, список их не отдаёт — карточка очереди не может показать причину без второго запроса (для 5 demo-сигналов это приемлемо).
- Disclaimer и on-site checks правильные, но стоят под простынёй `message`.

### Где нет контекста

- Не сказано, что это один ЖК и три зоны наблюдения, а не три разных проекта.
- `created_at` сигнала = время `seed-demo` (`2026-09-20T14:39`), а наблюдения Корпуса 1 — `01/08/15/22.09`. «Когда это произошло» сейчас врёт, если взять `created_at`.
- Два `no_dynamics` и два `schedule_delay` на один корпус (срезы 15.09 и 22.09) выглядят как дубли, потому что на карточке нет контрольной даты.

### Первый проход: куда глаза не ведут

Открыл `/` → Котлован А. Увидел JSON `floors: 0` на котловане и таблицу `dump_truck 0.88`. Не сразу понял, что **норма — это совпадение техники**, а нули этажей ожидаемы на этапе котлована. Сигнал «ничего проверять не нужно» тонет в шуме полей, которые для этой зоны нерелевантны.

## 3. Information architecture

Не копировать сущности БД (`Observation`, `ActualStateRecord`, `DeviationRecord`). Навигация — по работе инспектора.

### Рекомендуемая структура (3 раздела)

```text
Обзор          ← дом, ответ на «что сейчас?»
Сигналы        ← работа: очередь + карточка + решение
Объекты        ← площадка как целое (зона = единица наблюдения)
```

Четвёртый пункт «Инспекция» как корневой раздел **не нужен**: инспекция — это экран сигнала, не раздел продукта.  
`Timeline` — вкладка/якорь страницы объекта, не пункт меню.  
`Alerts` и `Очередь инспектора` — один раздел «Сигналы».

Допустимые URL (frontend-агент может маппить на текущие файлы):

| URL | Экран |
|-----|--------|
| `/` | Обзор |
| `/signals` | Очередь сигналов |
| `/signals/:alertId` | Инспекция (detail). Deep link с Обзора и Объекта |
| `/objects` | Если один проект — сразу редирект на первую зону или сетка зон |
| `/objects/:zoneCode` | Страница зоны. Query `?tab=history\|evidence` |

Пока один проект `site_001` — переключатель проектов не строить. Имя проекта живёт в шапке.

### Почему не «Обзор / Объекты / Сигналы / Инспекция»

Четыре пункта снова размажут одно действие. Инспектор либо смотрит площадку, либо разбирает сигнал. Третий режим — обзор «с чего начать». Это максимум.

### Шапка приложения (постоянно)

```text
[Скрипка]     ЖК Северный                    [5 требуют проверки]
 Обзор   Сигналы   Объекты
```

- Счётчик в шапке = `alert_counts.open` из `GET /api/projects`.
- Клик по счётчику → `/signals`.
- Под брендом одна строка, не pipeline: «План, факт и основание для проверки».

### 3.1 Обзор `/`

**Цель.** За 30 секунд понять, где проверка нужна, а где нет.  
**Главный вопрос.** Что требует внимания прямо сейчас?  
**Primary action.** Открыть сигнал из блока «Сейчас требуют внимания».  
**Secondary.** Открыть зону; отфильтровать очередь по зоне.  
**Основная информация.** Карточки открытых сигналов (не KPI), затем состояние трёх зон, затем последняя съёмка.

Не класть сюда форму решения, JSON, таблицу детекций, fingerprint.

### 3.2 Сигналы `/signals`

**Цель.** Разбирать очередь: понять причину, посмотреть кадры, зафиксировать решение.  
**Главный вопрос.** Что проверить и какое решение я фиксирую?  
**Primary.** Выбрать сигнал → «Зафиксировать решение».  
**Secondary.** Фильтр статуса; открыть зону; сравнить кадры.  
**Основная информация.** Список карточек слева, инспекционный экран справа (на ≥1280px). На узком — список, затем full-page detail.

Фильтры (уже есть в `inspector.yaml` / `/api/inspector/config`):

- Требует проверки (`open`) — default
- Нужны дополнительные данные
- Подтверждено инспектором
- Отклонено инспектором
- Все

Не делать отдельную страницу «Alerts». Текущий `/alerts` — alias `/signals`.

### 3.3 Объект `/objects/:zone`

**Цель.** Увидеть зону как целое: этап, план/факт, активные сигналы, историю, кадры.  
**Главный вопрос.** Что должно быть на этой зоне и что видно сейчас?  
**Primary.** Открыть активный сигнал; если сигналов нет — ничего не делать (это норма).  
**Secondary.** Переключить зону; вкладка истории; сравнение кадров.  
**Основная информация.** Header зоны, Plan vs Fact текущего среза, список сигналов, лента дат, превью кадра.

Переключатель зон — сегмент или select **с человеческими именами**, без `DEMO 1 — NORMAL`.

### Что удалить из навигации

| Сейчас | Куда девается |
|--------|----------------|
| Инспекция `/` | Содержимое распределяется: сравнение — на Объект и Сигнал; `/` становится Обзором |
| Dashboard | Это и есть Обзор |
| Очередь + Alerts | Сигналы |
| Timeline | Вкладка «История» на Объекте |
| Объект | Остаётся, но перестаёт быть JSON |

## 4. Dashboard (Обзор)

Инспектор видит **первым** не метрики, а ситуации, которые просят его внимания.

### Иерархия

```text
LEVEL 1  Сейчас требуют внимания     ← 70% первого экрана
LEVEL 2  Состояние зон
LEVEL 3  Недавняя съёмка
LEVEL 4  Система                     ← внизу, мелким
```

### LEVEL 1 — Сейчас требуют внимания

Заголовок: **Сейчас требуют внимания**  
Подзаголовок: `5 ситуаций · решение принимает инспектор`

Сортировка карточек (frontend, без новой логики правил):

1. `building_01` + `no_dynamics` с самым поздним наблюдением (22.09) — главный demo-case
2. `building_01` + `schedule_delay` на ту же дату
3. `zone_b` + `missing_equipment`
4. Более ранние срезы Корпуса 1 (15.09) — ниже, визуально вторичные

На Обзоре **не показывать все 5 одинаково**. Показать:

- 1 большую карточку Корпуса 1 (см. §5.2, вариант «сводка корпуса»: оба типа на 22.09 в одной карточке-саммари **или** две карточки, но первая — no_dynamics 22.09 на всю ширину)
- затем компактные карточки остальных `open`

Рекомендация для demo: **одна hero-карточка Корпуса 1** + список остальных.

Hero Корпус 1 (выше fold):

```text
[требуется проверка]  Динамика не наблюдается
Корпус 1 · Надземная часть · камера корпуса · 22.09.2026

┌ Ожидалось          ┐   ┌ Наблюдается        ┐
│ 6 этажей           │   │ 4 этажа            │
│ КСГ: 4 → 6 за 21 д.│   │ 4 → 4, без прироста│
└────────────────────┘   └────────────────────┘

[thumb 01.09] [thumb 08.09] [thumb 15.09] [thumb 22.09]
                                               ↑ текущий

Плюс вторичная строка: «Также: возможное отставание от графика (план 6 / факт 4)»

[Разбрать сигнал]
```

Данные hero:

| Показать | Скрыть |
|----------|--------|
| type label, zone **name**, stage_label, дата последнего кадра | `site_001`, zone code, fingerprint, UUID |
| Plan vs Fact по этажам | `schedule_progress`, `change_score`, `visual_change` |

| duration: «21 день наблюдений» из `observed.observation_period_days` | `created_at` сида |
| CTA «Разбрать сигнал» → `/signals/:id` | JSON |

Остальные карточки LEVEL 1 — формат Alert Card (§5), компактный.

Пустое состояние (после разбора всех `open`): крупно «Очередь пуста. Ситуаций, требующих проверки, нет.» и LEVEL 2.

### LEVEL 2 — Состояние зон

Три карточки одинаковой ширины, разный статус.

**Поля карточки зоны**

```text
[status icon + label]
Имя зоны                         Котлован А
Этап                             Разработка котлована
План vs факт (1–2 метрики)       см. ниже
Открытых сигналов                0 / 1 / 2 (только open)
Последний кадр [72×48 thumb]     дата+время наблюдения
[Открыть зону]
```

Метрики по зоне (не все ключи ActualState):

| Зона | Показать | Не показывать |
|------|----------|----------------|
| Котлован А | техника: экскаватор 1/1, самосвал 3/≥2 | floors/columns/slabs = 0 |
| Котлован Б | самосвал **0 / ≥2** (акцент), экскаватор 1/1 | нули остальных машин |
| Корпус 1 | этажи **4 / 6**, плиты 4 / 6 | полный список equipment с нулями |

Статус зоны (вычислить на frontend из API, не новая domain-логика):

| Условие | Статус UI |
|---------|-----------|
| `open_alerts === 0` | `normal` — «Проверка не требуется» |
| есть open `missing_equipment` / `schedule_delay` / `no_dynamics` / `missing_element` | `attention` — «Требует проверки» |
| только `insufficient_evidence` | `insufficient` — «Недостаточно данных» |
| open=0 и все сигналы `confirmed` | `confirmed` не на зоне, а на сигналах; зона → `normal` + строка «последнее решение: подтверждено» |

`zone.stage` в dashboard сейчас английский enum. Брать `last_expected.stage_label`.

JSON на карточке зоны **запрещён**.

Не делать 8 metric-плиток. Если очень нужно одно число сверху LEVEL 1 — только «5 требуют проверки». Плитки «Подтверждено 0 / Отклонено 0» — LEVEL 4 или фильтры в Сигналах.

### LEVEL 3 — Недавняя съёмка

Горизонтальная лента из последних наблюдений по всем зонам (из трёх `GET .../zones/:code`, поле `observations[0]` уже newest).

```text
[thumb] Корпус 1 · 22.09 12:00 · 4 этажа
[thumb] Котлован Б · 18.09 11:20 · самосвалы 0
[thumb] Котлован А · 18.09 10:40 · норма
```

Клик → объект, якорь на кадр. Видео `zone_a_window.mp4`: не `<img src=mp4>`. Показать `viz_url` как постер + бейдж «видео».

### LEVEL 4 — Система

Мелко, без акцента:

- Объект: ЖК Северный · Москва, демо-площадка
- Зон: 3
- Детектор в demo: не выводить `annotation` пользователю. В технических деталях — можно.

## 5. Alerts

### 5.1 Очередь

Слева список карточек, справа detail. Текущий `/queue` — правильный каркас, неправильное содержимое карточки (только тип + `building_01`).

Карточка списка — не две строки. Высота ~88–104px.

### 5.2 Alert Card — поля сверху вниз

Общий скелет. Не абстракция: это конкретный layout.

```text
┌─────────────────────────────────────────────────────────────┐
│ [иконка статуса]  {title_ru}                 [severity text]│
│ {Имя зоны} · {этап} · {контрольная дата}                    │
│                                                             │
│   Ожидалось                    Наблюдается                  │
│   {expected_primary}           {observed_primary}           │
│   {expected_secondary}         {observed_secondary}         │
│                                                             │
│ {duration_line}                                             │
│ [thumbnail 160×100]  Последний кадр {HH:MM, DD.MM}          │
│                                                             │
│ [Разбрать]   при необходимости [Открыть зону]               │
└─────────────────────────────────────────────────────────────┘
```

**Показать:** type→title, zone name, stage_label, Plan vs Fact, duration, thumb, last frame time, CTA.  
**Скрыть в карточке:** message целиком, fingerprint, UUID, rule_id, confidence triple, evidence id list, `object_id: site_001`, английский rationale.

`title` брать так:

1. словарь §12 по `type` (короткий заголовок карточки)
2. `deviation.title` из detail — можно в подзаголовок detail, не дублировать слово в слово с `message`

#### Вариант A — `missing_equipment` (zone_b)

```text
[внимание]  Недостаточное количество техники

Котлован Б · Разработка котлована · 18.09.2026

Ожидалось                    Наблюдается
≥ 2 самосвала                0

Экскаватор (норма) 1         Экскаватор 1

По кадрам 18.09, 11:10–11:20
[кадр котлована без самосвалов]
Последний кадр: 11:20

[Разбрать]
```

Маппинг DTO `GET /alerts/:id`:

| UI | Поле |
|----|------|
| expected_primary | `deviation.expected.dump_truck` → «≥ {n} самосвала» (это min_count) |
| observed_primary | `deviation.observed.dump_truck` |
| thumb | `evidence[-1].viz_url \|\| evidence[-1].media_url` |
| last frame | `evidence[-1].timestamp` |
| duration | если один день — «по кадрам {date}»; не использовать `created_at` |

## 8. Timeline

Это не список backend events и не колонка «сигналы дня» с полным `message`.

### Проблема текущей модели

`GET /timeline` вешает alert на каждый `related_dates[]`. У `no_dynamics` related_dates = `01, 08, 15, 22.09`, поэтому **01.09 помечен «Нет динамики»**, хотя в этот день план=факт. Для инспектора это ложный маркер.

## 10. Plan vs Fact pattern

Это **язык Скрипка**. Один компонент, разные слоты.

### Имя в коде

`PlanFactComparison`

Не «метрика», не «JSON diff», не таблица всех ключей.

### Анатомия

```text
┌──────────────────────┬──────────────────────┐
│ Ожидалось            │ Наблюдается          │
│ {operator}{value}    │ {value}              │
│ {unit / label}       │ {unit / label}       │
│ {secondary}          │ {secondary}          │
└──────────────────────┴──────────────────────┘
{match: совпадает | расхождение | данных мало}
{limitation?}
```

Для динамики (третий вид) те же две колонки, secondary несёт интервал:

```text
Ожидалось                    Наблюдается
+2 этажа                     0 изменений
за 21 день по КСГ            4 кадра, одна камера
```

### Почему не только «VS»

Слово «VS» допустимо между колонками. Заголовки колонок зависят от типа:

| Тип сигнала / зона | Левая колонка | Правая |
|--------------------|---------------|--------|
| техника | Ожидалось | Наблюдается |
| этажность / КСГ | План | Факт |
| динамика | Ожидалось по графику | Наблюдается |

В одном компоненте проп `mode: 'expected_observed' | 'plan_fact' | 'dynamics'`.

### Reusable data (frontend helper, не engine)

Собрать массив строк сравнения. Не тащить все ключи ActualState.

```text
ComparisonRow {
  id: 'dump_truck' | 'floors' | 'slabs' | 'floors_delta' | ...
  label: string            // «Самосвалы», «Этажи»
  expectedValue: string    // «≥ 2», «6», «+2»
  observedValue: string    // «0», «4», «0»
  tone: 'match' | 'gap' | 'unknown'
}
```

Правила отбора ключей:

- Зона котлована: только `required_equipment` vs `actual.equipment` тех же типов. Нулевые `roller`, `bulldozer`, … не показывать.
- Корпус, сигнал delay: ключи из `deviation.expected` / `observed` (`floors`, `slabs`). Не выводить `walls: 0`.
- Корпус, динамика: одна строка этажей + secondary про период. Не выводить `stable_elements: [foundation, columns, …]`.
- `schedule_progress` **не является row**.

Маппинг min_count: в `deviation.expected` для техники число = минимум. В UI всегда префикс «≥», если тип `missing_equipment`.

Tone:

- match: факт ≥ минимума техники или факт ≥ плана присутствия; этажи равны
- gap: факт ниже плана / минимума; дельта этажей 0 при росте КСГ
- unknown: `insufficient_evidence`

Цвет не единственный носитель: иконка совпадения / расхождения + текст «совпадает» / «расхождение».

### Где используется

Обзор (hero + зона), Alert Card, Inspection, Object «Состояние», Timeline (как числа под рельсами).

`PlanFactTable` в текущем виде **заменяется** этим паттерном + рельсами дат. Не оставлять обе таблицы.
